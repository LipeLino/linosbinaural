Implement authentication, private saves, public sharing, account management, and database security.

E. Monetization:
Implement sandbox checkout, webhook handling, entitlement restoration, ad gating, consent, and configuration states.

F. Production hardening:
Complete localization, accessibility, error states, legal/configuration pages, security headers, and subpath integration.

G. Verification and deployment:
Run the acceptance suite, repair findings, create final artifacts, and deploy if the deployment gates are satisfied.

Do not stop at a scaffold, mock data demonstration, or “next steps” list while executable implementation remains.


18. VERIFICATION AND ACCEPTANCE

Build a traceable acceptance matrix. Every required journey must have evidence, not just a checkmark.

Run relevant checks during development and a complete production-oriented suite before delivery.

Audio verification:
- Frequency and channel-routing tests.
- No unwanted opposite-channel carrier leakage introduced by the app.
- Correct behavior at supported sample rates.
- Gain transitions, waveform changes, and preset switching.
- Worst-case summed output and clipping protection.
- Timed fades and termination.
- Pause/resume and repeated start/stop cleanup.
- Asset-loading failures.
- Bounded resource use during a documented soak test.

Use OfflineAudioContext or another suitable real signal test, not merely mocked “play was called” assertions.

Do not claim that a browser screenshot verifies audio quality. Distinguish signal-level tests from human listening checks not actually performed.

Database/security:
- Test anonymous access, User A, User B, and privileged webhook access separately.
- Prove User B cannot read or modify User A’s private presets.
- Prove publication and unpublication behave correctly.
- Prove ordinary users cannot assign themselves ad-free access.
- Validate direct database/API paths, not only hidden buttons.

Payments:
- Both fixed currencies.
- Successful, pending, cancelled, and failed checkout.
- Tampered price inputs.
- Invalid webhook signatures.
- Duplicate and out-of-order events.
- Reconciliation after a delayed webhook.
- Restore entitlement on another session.
- Refund/dispute handling.
- No ad requests for an entitled account.

Browser:
- Test the actual /linosbinaural path.
- Guest play and ambience mixing.
- Account registration/recovery where external email is configured.
- Save, reload, publish, open in another session, and unpublish.
- Mobile navigation and ambience panel.
- Network failures and interrupted sessions.
- No serious console errors, failed required requests, or hydration errors.
- Validate a production build, not just a development server.

Visual review:
Capture and personally inspect representative pages at:
- 360 or 390 pixels wide.
- 768 pixels wide.
- 1280 pixels wide.
- 1440 or 1920 pixels wide.

Inspect day/night themes, both languages, empty/saved shelves, a long preset title, dialogs, error states, and a configured ad-slot preview.

Evaluate:
- Is this recognizably an original pixel-art listening room?
- Are the binaural mixer and ambience panel obvious?
- Do the presets really read as records on open shelves?
- Are textures, sprites, perspective, and lighting coherent?
- Are text and controls readable without effort?
- Does mobile feel designed rather than compressed?
- Is the result distinctive without becoming cumbersome?

Perform one focused independent review of high-risk code and one deliberate final visual review. Repair identified problems and rerun affected tests.

Avoid endless taste reviews or repeated audits with no new evidence. Do not lower acceptance criteria to make the project appear finished.


19. HUMAN-ONLY BLOCKERS

Use docs/dev-to-do.md only for tasks you genuinely cannot perform.

Each entry must state:
- Exact blocked capability.
- Why current tools/access cannot complete it.
- What was attempted.
- Required service/account setting.
- Step-by-step action for me.
- How to verify success afterward.
- Whether it blocks general deployment or only a feature such as live payments.

Typical legitimate examples:
Merchant identity verification, missing account authorization, sender-domain verification without DNS access, ad-network approval, or approval for a paid hosting plan.

Not legitimate examples:
Writing migrations, implementing checkout, fixing CSS, creating original icons, testing RLS, wiring a webhook, or documenting a deployment command.

When an external integration is unavailable, finish its real implementation and tests using appropriate local/sandbox facilities. Keep the live feature safely disabled and report its status accurately.

Never replace a missing integration with a fake success path.
